# 设计说明书

> 本文件是骨架稿：结构、接口、算法说明齐了，具体措辞可再改。每节都标了实现位置，便于对照代码。
> 唯一的工程记录（节点、判据、实测、边界）在 `目标树.md`；本文件只讲"系统怎么设计"。

## 1 目标与范围

系统输入一句中文描述，输出一段连续的人体运动视频（含分镜与验证记录）。

```
范围之内   分镜规划、动作生成调度、关节解码、体型与姿态拟合、段间装配、渲染、后处理、质量判定
范围之外   动作生成模型本身的训练与改进（视为外部能力）；真实场景重建；多人物交互
```

设计主张：**大模型只做"组织"这一层**（拆段、选词、挑候选、决定合并与修补、解释失败），
它不改写底层生成模型，而是把不可控的模型组织成可控的管线。

## 2 总体设计

```
一句中文
   │
   ▼
[A01–A02] 规划：planner → 分镜（段、提示词、帧数、原文片段）
   │        hm/planner.py、hm/planner_prompt.py、hm/planner_fallback.py
   ▼
[A03–A06] 支持性判定 → 路由 → 提示词规范化 → 短段合并
   │        hm/run_job.py（step_a03/a05/a06、ensure_stop_frames、merge_short_segments）
   ▼
[A07–A12] 生成候选 → 几何/姿态检查 → 选择（签名排序 + 交界最优 DP）
   │        hm/generate.py、hm/criteria_v2.py、hm/signature.py、hm/finish_job.py
   ▼
[A13–A18] 失败分类与修补 → 解析 IK 拟合 → 参数空间装配（过渡/截尾/修复）→ 渲染
   │        hm/fit.py、hm/ik_init.py、hm/shape.py、hm/assemble_params.py、hm/render_blender.py
   ▼
[A19] 后处理：裁切、字幕角标、分镜图、语义验证记录
          hm/main.py、frame_crop.py、annotate_video.py、job_report.py
```

## 3 接口设计

### 3.1 命令行

```
python -m hm.main "句子" [--k 6] [--job-id 名字]     正常出片
python -m hm.main "句子" --explain                    只规划，说明能保证什么
python -m hm.main "句子" --compare                    预测与实际并排
python -m hm.main --check / --batch 文件              冒烟 / 批量
python -m hm.guard / hm.selfcheck / hm.capability_report
```

出口码：`0` 正常；`1` 出片但有可疑或近似代替的段；`2` 未出片。

### 3.2 后端契约

注册表 `hm/backends.py`：名字 → 入口、最大帧数、是否支持种子/条件生成、契约（hml263 / 20fps / 米 / 22 关节）。

```
切换方式   HM_FORCE_BACKEND=<名字>（不认识的直接报错并列出已注册项）
契约校验   hm/criteria_backend.contract_ok()，不满足契约的拒绝进入主链
按后端校准 hm/calibrate_backend.py 产出 criteria_<backend>.json，阈值取自该后端自己的分布
```

### 3.3 产物契约

```
outputs/<job>/
  storyboard.json     分镜与选择结果（可追溯：每段 prompt、source、候选、选中项）
  assembled/          params.npy、joints22.npy、bounds.json（交界、过渡帧数）、metrics.json
  render/             final.mp4 → final_cropped.mp4 → final_captioned.mp4
  semantics.json      逐段语义状态：通过 / 未验证 / 可疑 / 未选中（含原因）
  分镜.png            每格标题带状态角标
  run.log             逐步日志（含失败类型与修补决策）
```

## 4 关键设计

### 4.1 规划：把"能做什么"写进提示词

`hm/planner_prompt.py` 把实测能力清单（44 个可用动作 + 6 个死路）作为 `<capability_list>` 交给大模型，
并给 3 个示例（含一个必须"近似"的例子）、自检清单与固定输出格式。
原文放在 `<text>` 里，要求 `source` 逐字摘录——**可追溯性靠这一条**。
大模型不可用时 `hm/planner_fallback.py` 用中文动作词表兜底，能力更弱但不出空白。

### 4.2 路由与措辞

`hm/backends.resolve()` 按能力表挑后端；复合条目（如"坐下再站起"）不外推。
`hm/prompt_normalize.py` 只做两类有实测依据的改写：出拳补出手、停住句去掉 `in place`。
历史教训：放开改写曾三次改错语义（crawl→push 等），所以范围被刻意限死。

### 4.3 片段合并（替换"拼接"）

相邻两段都短（或合计 ≤120 帧）且提示词本身不是复合句时，合成为一段，用复合提示词生成——
直接消掉一个交界。代价是合并段无法逐动作检查，所以：

```
1 选择时优先"两个动作都做出来"的候选（allowed 名单），DP 也只在名单内挑
2 没有任何候选满足 → 退回未合并的两段重新生成（宁可留交界，不可丢动作）
3 守门的 merged 项每次检查这条约束
```

### 4.4 拟合：解析 IK + 体型反解

`hm/ik_init.py` 最小弧解析 IK（单子关节用最小弧、多子关节用 Kabsch），`hm/shape.py` 由骨长反解 betas。
实测关节误差 1.6–1.8 cm，单段 0.2 s。否证过：Kabsch 单子关节版产生 70.8 °/帧高频扭转；
初值多迭代 2 轮只换来 0.1 cm 却多 2.7 s。

### 4.5 装配与过渡

参数空间 slerp + hermite 曲线，过渡帧数由"姿态差 / 两侧速率"决定，并设两条约束：

```
速度一致   过渡速率 ≤ 1.4 × 两侧速率（判据：速率比落在 0.7–1.4 为合格）
截尾       交界差 >60° 时试截前段末尾 2–12 帧，只在"交界变小且本段动作仍成立"时采纳
交界修复   差 >90° 时给后段补候选，挑最贴合者；实测收益 5–10°，属兜底
```

### 4.6 质量判定：三层判据

```
层一 物理必然   骨长恒定、数值有限、形状正确 → 硬门禁
层二 校准判据   动作签名（走/转身/坐/蹲/弯腰/跳/踢腿/出拳/停住）——每条都在正负对照上校准过
层三 绝对物理量 姿态差、加速度比 → 只记录、只排序，不做门禁
覆盖不到的动作（举手/推拉/捡取/复合描述）显式标"无法判"，并说明为什么分不开
```

### 4.7 可追溯与"说实话"

```
每段  prompt（英文）+ source（原文逐字）+ label（含"近似："）+ 语义状态
合并段  按拆开的子动作分别判定：不合格→可疑，无法判→未验证，两者都不算"通过"
近似段  原文动作做不出来时用最接近动作代替，标"近似"，出口码记 1
```

## 6 已知限制

```
握拳       SMPL 刚体手，表示层做不到（要 SMPL-X/MANO + 手指数据）
对象操作   揉面、撒粉、坐椅子等只能近似，label 会写"近似：…"
兽类/情绪  给出最接近的人体动作，非原意
死路动作   爬行/蹲下/躺下/跳舞通过率 0，规划阶段就拦下
语义覆盖   78%（标准集）：举手、推拉、捡取、复合描述没有可分量的量
人判       语义正确率仍需人工盲评（39 个片段，见 tools/blind_review.py）
```
